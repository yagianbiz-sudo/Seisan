# おくりむかえ帳 v1（公開版Webアプリ）開発指示書

この文書は、開発を担当するClaudeセッション向けの指示書です。上から順に読み、マイルストーン（M1〜M7）を1つずつ完了させてください。

## 0. 前提と進め方

- **オーナー**はアプリの発案者で、開発の知識はありません。質問や作業依頼は日本語で、専門用語を避け、画面のどこを押すかまで具体的に書いてください。
- **試作版**は `sougei/index.html`（1ファイル、バニラJS）です。画面構成、文言、配色、トレードの考え方はこれを正としてください。迷ったら試作版の挙動に合わせます。
- 作業場所はこのリポジトリの `sougei/app/` です（リポジトリ直下には別プロジェクト `choruko/` があるので触らないこと）。
- マイルストーンごとにコミットして push してください。ブランチ運用はセッションの指示に従います。
- 各マイルストーンの「完了条件」をすべて満たしたら、オーナーへ「できたこと／オーナーが確認すること／次にやること」を短く報告してください。
- この文書にない判断が必要になったら、勝手に広げずオーナーに聞いてください。ただし、技術的な細部（ライブラリの小さな選定など）は自分で決めてかまいません。

## 1. プロダクトの目的

夫婦で保育園の送迎を分担するとき、どちらが何回行ったかが見えないこと、そして「下の子やるよ」のような言葉足らずの交代でトラブルになることを解決します。

1. 基本の送迎パターンを登録すると、毎日の担当が自動で入る
2. 毎日の担当をふたりで同じ画面で確認できる
3. 予定変更は「トレード依頼カード」で相手に頼む。**相手が「受ける」を押すまで担当は変わらない**。成立後に何がどう変わるかを、送信前に必ず明示する
4. 月ごとの送迎回数を数字で比べられる。貸し借りも記録する

**設計の芯となるルール：自分の担当を相手に移すには、必ず相手の承認が必要。相手の担当を自分が引き受けるのは、いつでも一方的にできる。**

## 2. 確定した設計判断

| 項目 | 決定 |
|---|---|
| 形態 | PWA（ホーム画面に追加できるWebアプリ）。iPhoneアプリ化はv1の後で、Capacitorで包む前提 |
| フロント | Vite + React + TypeScript（strict）、`vite-plugin-pwa` |
| バックエンド | Firebase（Authentication / Firestore / Cloud Functions（Node 20, TypeScript）/ Cloud Messaging / Hosting） |
| リージョン | Firestore・Functions ともに `asia-northeast1`（東京） |
| タイムゾーン | 日付の扱いはすべて `Asia/Tokyo` 固定。日付キーは `YYYY-MM-DD` の文字列 |
| ログイン | Googleログイン + メールリンク（パスワードなし）。Appleでサインインはアプリ化のときに追加 |
| 世帯の人数 | v1は**2人固定**（スロット `a` / `b`）。祖父母など3人目以降は将来対応。データ構造は拡張しやすくしておく |
| 回数の数え方 | 「子ども1人 × 送り or 迎え」を1回とする（試作版と同じ）。2人まとめて送っても2回 |
| 過去の記録 | パターンを変更しても過去の回数が変わらないよう、パターンは「適用開始日つきの版」で持つ（§4） |
| 書き込み方針 | 世帯設定と日ごとの予定はクライアントから直接書く（セキュリティルールで保護）。**トレードの作成・回答・取り消し・引き受けは、すべてCallable Functions経由**（トランザクションと通知を1か所にまとめるため） |
| 言語 | UIは日本語のみ |
| 環境 | Firebaseプロジェクトは `okurimukae-dev` と `okurimukae-prod` の2つ（名前はオーナーが作成時に決めてよい） |

## 3. 画面と機能（v1の範囲）

試作版の4タブ（予定 / トレード / 集計 / 設定）を引き継ぎます。追加・変更点は次のとおりです。

1. **ログイン画面**：Googleとメールリンクの2つ。アプリの説明を1〜2行
2. **はじめての設定**
   - 「世帯をつくる」か「招待コードで参加する」を選ぶ
   - 世帯をつくる人がスロット `a` になり、試作版と同じパターン登録をする
   - 登録が終わったら招待画面を出す。招待は**6桁の英数字コード + 共有用リンク**で、有効期限は72時間、使えるのは1回だけ
   - 参加した人がスロット `b`。自分の呼び名を入力する
   - 試作版の「あなたはどちら？」画面は廃止（ログインしたユーザーで決まる）
3. **予定**：試作版どおり。相手がまだ参加していない間は「招待コードを送ってください」バナーを出し、トレード依頼はできないようにする
4. **トレード**：試作版どおり。加えて次のふるまいにする
   - 同じ担当に出せる依頼は、返事待ちのものが1件まで
   - 依頼対象の日付が過ぎたら自動で「期限切れ」になる
   - 受ける時点で担当が依頼時と変わっていたら成立させない。`expired` にして「予定が変わったため、この依頼は成立できませんでした」と表示する（お返しの担当についても同様に確認する）
   - 受ける・断る・取り消すを同時に押されても二重に成立しない（トランザクションで処理する）
5. **集計**：試作版どおり。加えて、月の切り替えは世帯の開始月より前には戻れないようにする
6. **設定**
   - パターン変更時に「いつから適用するか」を選ばせる（既定は今日）。過去日は選べない
   - 子どもの削除は論理削除（`archived: true`）。過去の集計には名前を残す
   - 通知のオン・オフ
   - 招待コードの再発行（相手が未参加のときだけ）
   - ログアウト
   - **アカウント削除**（後述）
   - 利用規約・プライバシーポリシーへのリンク
7. **通知（Web Push / FCM）**
   - 依頼が届いた：「◯◯さんからトレード依頼：10/24(金) 下の子の送り」
   - 依頼が成立した／断られた
   - 相手が担当を引き受けてくれた
   - iPhoneではホーム画面に追加しないと通知が届かないため、通知をオンにする画面で追加手順を図解する
   - 通知を押したらトレード画面を開く
8. **アカウント削除**
   - ユーザーを世帯から外し、認証情報とFCMトークンを削除する
   - 世帯に誰も残らなければ、世帯のデータ（サブコレクションを含む）をすべて削除する
   - 確認は画面内のダイアログで行う（`confirm()` は使わない）
9. **オフライン**：Firestoreのオフライン永続化を有効にし、閲覧はできるようにする。トレード操作は「オンラインのときに操作してください」と表示する

**v1でやらないこと**：3人目以降の保護者、カレンダー連携、雨の日ルール、朝のリマインド通知、ネイティブアプリ、試作版データの移行、多言語対応、課金。

## 4. データモデル（Firestore）

```
users/{uid}
  displayName: string
  householdId: string | null
  slot: 'a' | 'b' | null
  notify: boolean
  createdAt: Timestamp

users/{uid}/fcmTokens/{token}
  createdAt, userAgent

households/{hid}
  memberUids: string[]                 // ルール判定用（最大2件）
  members: { [uid]: 'a' | 'b' }
  names: { a: string, b: string }      // 呼び名
  kids: [{ id, name, school, archived: boolean }]
  schedules: [                         // 適用開始日の昇順。末尾が最新
    { from: 'YYYY-MM-DD',
      weekdays: number[],              // 0=日 … 6=土
      pattern: { [weekday]: { ['<kidId>-drop' | '<kidId>-pick']: 'a' | 'b' } } }
  ]
  startDate: 'YYYY-MM-DD'
  createdAt: Timestamp

households/{hid}/days/{YYYY-MM-DD}
  legs?: { ['<kidId>-<leg>']: 'a' | 'b' }   // パターンからの上書きだけ
  off?: boolean                             // 送迎なし

households/{hid}/trades/{tradeId}
  kind: 'request' | 'take'
  from: 'a' | 'b'           // 元の担当者（担当を手放す側）
  to:   'a' | 'b'           // 新しい担当者
  date, kid, leg            // 対象の担当
  ret: { date, kid, leg } | null   // お返し（成立すると from が担当する）
  note: string              // 最大140文字
  status: 'pending' | 'accepted' | 'declined' | 'cancelled' | 'expired'
  createdBy: uid
  createdAt, answeredAt?: Timestamp

invites/{code}
  householdId, createdBy, expiresAt, usedBy?: uid
```

**担当の決め方**（純粋関数として `src/domain/` に置き、UIとFunctionsの両方から使う）：

1. その日が `startDate` より前なら対象外
2. その日に有効な schedule は、`from <= 日付` を満たすものの中で最後のもの
3. その schedule の `weekdays` に含まれない日、または `days/{日付}.off == true` の日は送迎なし
4. 担当は `days/{日付}.legs[key]` があればそれ、なければ schedule の `pattern[曜日][key]`
5. 子どもはその日に `archived` でないもの。ただし `days` に上書きがある子は表示する

**貸し借り**：`status == 'accepted'` かつ `ret == null` のトレード1件につき、`from` が `to` に借り1回（試作版と同じ）。

## 5. セキュリティルールとFunctions

- `households/{hid}` とそのサブコレクションは、`memberUids` に含まれるユーザーだけが読める
- `households/{hid}` の更新：メンバーのみ。`memberUids` と `members` はFunctions経由でしか変更できない
- `days`：メンバーのみ書き込み可。ただし**自分の担当を相手に移す書き込みはルールで拒否する**（`legs` の値が自分のスロット以外に変わる変更は不可。担当の移動はトレードのFunctionsが行う）。`off` の切り替えはメンバーなら可
- `trades`：クライアントからの書き込みはすべて不可（Functionsのみ）
- `invites`：クライアントからは読み書き不可（Functionsのみ）
- `users/{uid}`：本人のみ読み書き可。ただし `householdId` と `slot` はFunctionsのみが変更できる

Callable Functions（すべて `asia-northeast1`）：

| 関数 | 内容 |
|---|---|
| `createHousehold` | 世帯を作り、呼び出した人を `a` にする |
| `createInvite` / `joinHousehold` | 招待コードの発行と、コードによる参加 |
| `requestTrade` | 依頼を作る。依頼者が現在の担当者か、同じ担当に返事待ちの依頼がないか、日付が今日以降かを確認する |
| `respondTrade` | 受ける・断る。トランザクションで、担当がまだ依頼時のままかを確認して `days` を更新する |
| `cancelTrade` | 依頼者による取り消し |
| `takeOver` | 相手の担当を引き受ける |
| `deleteAccount` | §3-8 の処理 |

ほかに、Firestoreトリガーでトレードの作成・状態変化時にFCMを送信します。毎日0:10（JST）に、日付が過ぎた `pending` を `expired` にするスケジュール関数も置きます。

## 6. マイルストーン

各マイルストーンの完了条件には、`npm run lint`、`npm run typecheck`、`npm test` がすべて通ることを含みます。

### M1 土台
- `sougei/app/` に Vite + React + TS、ESLint、Prettier、Vitest を用意する
- 試作版のデザイントークン（配色・フォント・ライト／ダーク）をCSS変数として移植する
- `src/domain/` に担当決定、月集計、貸し借りの純粋関数を作る
- **完了条件**：domain関数のユニットテスト（パターン版の切り替わり、お休み、上書き、archived、月またぎ、JSTの日付境界）が通る

### M2 Firebase接続とログイン
- 開発はFirebase Local Emulator Suite（Auth / Firestore / Functions）で行う。エミュレータにはJavaが必要なので、なければ導入手順をREADMEに書く
- ログイン画面、ログアウト、`users/{uid}` の作成
- `firebase.json`、`.firebaserc`、ルールファイル、`.env.example` を用意する。設定値（firebaseConfig）は環境変数から読み、リポジトリに秘密情報を入れない
- **完了条件**：エミュレータ上でGoogle（エミュレータ版）とメールリンクのログインができる

### M3 世帯と招待
- 世帯作成、パターン登録、招待コード、参加、セキュリティルール
- **完了条件**：`@firebase/rules-unit-testing` によるルールテストで、他世帯のデータが読めないこと、自分の担当を相手に移す `days` 書き込みが拒否されることなどを確認できる

### M4 予定・トレード・集計
- 試作版の3画面を移植し、トレード系のFunctionsを実装する
- **完了条件**：Functionsのテストで、二重成立しないこと、担当が変わっていたら `expired` になること、お返しつきで両方の担当が入れ替わることを確認できる

### M5 通知とPWA
- manifest、アイコン、Service Worker、FCM、通知設定画面、iPhone向けのホーム画面追加ガイド
- **完了条件**：エミュレータ以外（dev環境）で、Android Chrome と iPhone（ホーム画面に追加したもの）に依頼通知が届くことを、オーナーと一緒に確認する

### M6 アカウント削除・規約・仕上げ
- アカウント削除
- 利用規約とプライバシーポリシーの日本語の下書き（`sougei/app/public/` に静的ページとして置く）。取り扱う情報（呼び名、子どもの呼び名、園名、送迎記録、メールアドレス）、利用目的、第三者提供なし、Firebase（Google）の利用、削除方法、問い合わせ先（オーナーに確認）を含める。文書の先頭に「公開前に専門家の確認を推奨」と明記する
- 子どもの名前欄に「ニックネームでOK」と添える
- PlaywrightでE2Eスモークテスト（ログイン → 世帯作成 → 招待参加 → 依頼 → 成立 → 集計に反映）
- **完了条件**：上のE2Eがエミュレータ上で通る

### M7 公開
- GitHub Actionsで、mainへのマージ時にprodへデプロイし、PRごとにHostingのプレビューチャンネルを作る
- **完了条件**：オーナーがprodのURLで夫婦で使い始められる

## 7. オーナーにお願いする作業（その時が来たら、手順を1つずつ案内すること）

1. **M2の前**：Firebaseで dev / prod の2つのプロジェクトを作成し、Web アプリを登録して firebaseConfig を共有してもらう。Authentication で Google とメールリンクを有効化してもらう
2. **M4の前**：Functionsを使うため、Blaze（従量課金）プランへ切り替えてもらう。**予算アラート（例：月500円）の設定も必ず一緒に案内する**
3. **M5の前**：Cloud Messaging の Web Push 証明書（VAPIDキー）を発行してもらう
4. **M7の前**：GitHub リポジトリの Secrets に、デプロイ用サービスアカウントの鍵を登録してもらう。独自ドメインを使う場合は、その取得と接続
5. 問い合わせ用メールアドレスを決めてもらう

秘密情報（サービスアカウント鍵など）をチャットに貼ってもらわないこと。必ずGitHub Secretsやコンソール上で設定してもらいます。
